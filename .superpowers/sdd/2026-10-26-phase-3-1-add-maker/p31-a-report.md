## Under-specified points and my choices
1. **`email` is `not null`** (the plan says only "simple e-mail shape"): the prototype's `validateLogin` requires it («عليه بيوصل لينك التفعيل واسترجاع الباسورد») and both `store.create` and `store.setLogin` pass it. Capped at 120 chars like the prototype's `clean()`.
2. **`username` must already be lowercase** (the plan's regex is lowercase-only), so the unique index on `lower(username)` cannot be hit by a different-case duplicate through the API; it is still there as the plan says, and the plain duplicate → 23505 is tested.
3. **`created_by text`** (the member's display name), like `vendor_rates.set_by` / `vendor_bank.updated_by` — the adapter writes `actor.name`.
4. **`vendor_logins_update` uses `using (vendors.view <> 'N')`** and the permission in `with check` — the 0011 pattern — so a member who sees a row but may not change it gets 42501, not "0 rows" (the plan says "insert / update with `is_admin() or vendors.edit = 'F'`"; that is the with check).
5. **Order of checks in `set_password`**: 42501 → 22023 → **P0002 for a maker without a login row** (not in the plan; I did not want a silent no-op) → 0A000. The 128-char cap is mine (defensive bound on what reaches Vault).
6. **`reveal` logs before the read and even when it returns null** ("every call is on record"); a maker with no row → null, not an error.
7. **The secret lookup** is by the row's `secret_id`; a dangling id (secret removed outside this file) → a new secret; a `vault.secrets` row named `vendor-login:<uuid>` while the row's `secret_id` is null → reused. Nothing is ever deleted from Vault (plan: Later).
8. **The cascade is verified through the catalog** (`confdeltype = 'c'` on the fk, as `rls_vendors` does), not by deleting a maker — the standing rule says no `delete` in tests; the only `delete` text in `rls_vendor_logins` is the one the column grants refuse (run as text, like `rls_vendors`).
9. **`service_role` has execute on both RPCs** as the plan says, but their permission check is `is_admin() / has_perm` (needs `auth.uid()`), so a service_role call without a member JWT gets 42501. Written in the runbook; change it only by a decision (e.g. `or current_user = 'service_role'` for a future portal function).
10. **The test's Vault switch is decided as the runner**: `to_regclass('vault.decrypted_secrets')` run as `authenticated` raises "permission denied for schema vault" (the lookup checks USAGE even with missing_ok), so the member blocks read a transaction-scoped setting. Inside the RPCs the same call runs as the owner, which is fine. The stub run caught this.
11. **Test UUIDs …51–…56** as the brief says — `rls_mfa.sql` also uses …51–…56 for its own users; harmless (every file rolls back its own rows) but the two files share the range.

## Concerns for the reviewer
1. **The real Vault path has never run.** supabase_vault 0.3.1 on the live project (`vault.update_secret` has never been called there; 0008 only created a secret). The stub mirrors the 0.3.x signatures (`create_secret(new_secret, new_name, new_description, new_key_id)`, `update_secret(secret_id, new_secret, new_name, new_description, new_key_id)` with `coalesce` semantics) and `decrypted_secrets.decrypted_secret`. The live `rls_vendor_logins` run (§2.1 step 4) exercises it inside a rollback before any UI write — please run it before `main`.
2. **Orphan Vault secrets**: a maker deleted by cascade leaves `vendor-login:<uuid>` in `vault.secrets` (nothing deletes; Later list). Harmless but worth a line in the ledger.
3. **PostgREST upsert will not work on `vendor_logins`** with the brief's grant list (an `on conflict do update` of the payload needs UPDATE on `vendor_id` / `created_by`). Task B's `store.setLogin` must insert when `login` is null and PATCH otherwise (written in the migration header and the runbook). If the reviewer prefers an upsert-friendly grant, that is a decision (it would also let a client overwrite `created_by`).
4. **The guard's "portal" message** is reachable by ops (the BEFORE trigger runs before the with check), so a member without edit rights who sets `status = 'active'` reads that message instead of "policy". Harmless; the test for ops uses `username` so the policy message is what is asserted there.
5. **`migrate_0012` cannot exercise the drop path itself** (no drop allowed in tests); the drop runs once in CI's migration loop on the 0007 constraint and would fail that job loudly; the re-run (no-drop) path is what the file proves.
6. **Review Focus 1** (the password nowhere): the migration writes it only to Vault; `activity_log` rows carry null values; the test greps `old_value || new_value || action || entity_id` for the two test values. The RPC's `RAISE` messages never echo the password.
