## Under-specified points and the choice made

1. **UUIDs.** The brief says `…000061`–`…000068`; the file needs six members and five fixed makers. Members took `…61`–`…66`; makers took `…f1`–`…f5` (the block after `b`/`c`/`d`/`e` used by the earlier test files). Two further makers are inserted by name through the popup path (members cannot choose `vendors.id`).
2. **accounts and `sensitive.commission`.** The built-in matrix (0003) gives `sensitive.commission = F` to the admin only (accounts has `N`; `rls_vendors` asserts accounts reads zero `vendor_rates` rows). To test the `brand_rates` policy on a non-admin as the brief asks, the accounts test user carries `custom_perms {"sensitive.commission":"F"}` — the override the identity layer is designed for. Nothing in the matrix changed.
3. **No update policy / grant on `brand_owners`.** Decision 2 writes "insert/update" for brands/brand_owners in the RLS line but also "rows are only added, no update/delete for members" and grants `brand_owners` insert only; the guard is before insert only. I followed the add-only reading: no update policy and no update grant on `brand_owners` (and none on `brand_rates`). The test asserts exactly seven policies.
4. **`current owner` in the guard** = the owner of the latest row by `(since desc, id desc)`, not the owner "today" — a future-dated transfer already on file is the one a new row must differ from.
5. **The trigger never fails a maker's insert**: a taken / blank / over-80 name → no automatic brand, the vendors row goes in (the sync writes new stores through this trigger). The brand insert is `on conflict (lower(btrim(name))) do nothing` so two makers of the same name inserted at once make one brand. The backfill walks `created_at, id` so the older of two same-named existing rows gets the brand.
6. **`set_by = 'system'`** on the automatic owner row (the plan names `created_by = 'system'` for the brand only). A null date in the lookups reads as `current_date`.
7. **The select grants are table-level** (the plan says "select on every column"): nothing sensitive sits in the three tables, the rate is behind its own policy. The adapter should still name its columns (consistency with `vendors`), but `select=*` will not be refused here.

## Concerns for the reviewer

1. **`brand_owners.vendor_id` is `deferrable initially immediate` and `vendors` gained a before-delete guard, `vendors_brands_guard_delete`** (one function + one trigger beyond decision 2's list). Writing the cascade case showed that Postgres checks a plain NO ACTION key at the end of the statement but *before* the second-level cascade (`vendors → brands → brand_owners`) has removed the maker's own owner rows, so with the plan's design as written the origin maker could never be deleted at all (reproduced on a minimal schema). The guard refuses with 23503 (the message names `brand_owners_vendor_id_fkey`, like the key's own error) a maker found in the ownership history of a brand of another maker, and otherwise runs `set constraints public.brand_owners_vendor_id_fkey deferred` for the transaction so the cascade completes; inserts into `brand_owners` are still checked at once (initially immediate), and the commit-time check stays as a backstop. The guard is `security invoker`, applies to every role (an integrity rule, not a permission), reads the history as the caller (the delete policy admits the admin only, who sees every row). `rls_vendors`' own delete case (a maker with lines → 23503 from `sub_orders`) still passes.
2. **A past holder cannot be deleted either** (the history is never rewritten): a maker who held a brand temporarily and returned it stays referenced. Consistent with «عليه براندات», but the UI message should say "holds or held".
3. **Deleting the origin removes the brand even while another maker holds it** — this is decision 2 as written (`origin_vendor_id … on delete cascade`); the cascade takes the current holder's owner rows with it. The delete is admin-only and refused first while lines / sub-orders reference the maker, so on the live registry (every maker has a store) it is practically unreachable, but Task B's confirmation popup might mention it.
4. **The guards read under RLS**: `brand_owners_guard` (invoker) looks up the brand's last row as the member. A member with `vendors.edit = F` but `vendors.view = N` (only reachable by a contradictory `custom_perms`) would see no history and pass the `since` rule; the unique key still refuses duplicates. Same pattern as 0011 / 0012's guards.
5. **`store_owner_at` on a brand without owner rows** (cannot happen through this file — every brand insert path writes an owner row, and the API cannot delete owner rows) returns the store itself.
6. The RLS-live default now lists three files; the brief named `tools/db-test.sh` for "where the others are listed", but that script globs — flagged in case the controller prefers the workflow default untouched.

- `brand_rates`: `id bigint`, `brand_id uuid`, `rate numeric(5,2)|null`, `since date`, `set_by text|null`, `created_at`. Add-only; readable / writable only with `sensitive.commission = F` (a member without it gets **zero rows, not an error** on select; 42501 `policy` on insert).

**Writes the client may send (anything else is 42501 `permission denied for column/table`):**
- `insert brands (name, code, aliases, origin_vendor_id, created_by)` — `returning id` works (select is table-level).
- `update brands set name / code / aliases` (PATCH; `updated_at` bumps itself).
- `insert brand_owners (brand_id, vendor_id, since, return_on, reason, set_by)`.
- `insert brand_rates (brand_id, rate, since, set_by)` (`rate` null = no special rate from `since`).
- No delete on any of the three; no update on `brand_owners` / `brand_rates`.

**Error codes the client will see:**
- `23505` — duplicate brand name (constraint `brands_name_key`, compared on `lower(btrim(name))`); duplicate `(brand_id, since)` on `brand_owners` (`brand_owners_brand_id_since_key`) or `brand_rates` (`brand_rates_brand_id_since_key`); a second brand on the same store (`brands_store_vendor_id_key`, server only).
- `22023` with message exactly `since before the last transfer` or `same vendor` (from `brand_owners_guard`; the comparison is against the latest row by `since`).
- `23514` — `brand_owners_return_on_check` (`return_on <= since`), `brand_owners_reason_check` (> 200), `brands_name_check` (blank / > 80 after trim), `brands_code_check` (not `^[A-Z0-9]{1,3}$`), `brand_rates_rate_check` (outside 0–65).
- `42501` — policy refusals say `… violates row-level security policy …` (ops / accounts / viewer writing brands or owners; anyone without commission F writing rates); server columns say `permission denied for table/column …`; the guard's own message on `brands` (`brand columns owned by the server …`) is only reachable if the grants were widened.
- `23503` on deleting a maker: message contains `brand_owners_vendor_id_fkey` when the maker holds or held another maker's brand (from `vendors_brands_guard_delete`, raised at the delete statement) — distinguish from the existing 23503 of `sub_orders` / `order_items` by that substring. Deleting the origin of brands held by nobody else cascades (brands, owner rows, rates) with no error.

**Lookups (RPC-able, `authenticated`):** `brand_owner_at(p_brand uuid, p_date date) → uuid|null` (null date = today; null when the caller sees no history) and `store_owner_at(p_store uuid, p_date date) → uuid` (the store itself when it has no brand or the caller sees no history). The UI computes locally per the plan; the semantics to mirror: owner on D = last row with `since <= D` ordered by `(since desc, id desc)`, else the first row; `return_on` is informational — the return is a new row.

**The automatic brand:** inserting a vendor (popup) immediately yields a brand named `btrim(name)`, code = first Latin letter upper-cased else `X`, `aliases` = the vendor's, `store_vendor_id` null for hand-added makers, `created_by = 'system'`, one owner row `since = coalesce(joined_at, current_date)`, `set_by = 'system'`. When the name is already a brand name (case / trim-insensitive) no brand is created and the insert still succeeds — the adapter should reload brands after `create` and treat "no brand" as a valid state. The live backfill will produce 56 brands (55 tied to stores) owned by their makers since `joined_at`.
