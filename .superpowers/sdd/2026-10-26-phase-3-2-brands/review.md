### Important

**I1 — A brand's special rate is applied to orders dated *before* its first `since` (retroactive re-pricing of completed orders).**
- `app/js/adapter/vendors.js:153` (`brandRateAt`: `let r = b.rates[0].rate; for (const x of b.rates) if (!date || x.since <= date) r = x.rate;`) and `app/js/blocks/06-vendors-domain.js` `effectiveRate` (same rule, copied from the makers' `rateAt`).
- Failing scenario: Antikiano's store has a completed order on 10 Oct (no website rate on the line → our rate: the maker's 45%). Accounts sets a special rate of 30% on the brand «سارية من» 1 Nov. From that moment the 10 Oct order's share in «حقه من المكتملة» and the balance changes from 494.45 to 629.30, although the popup itself says «النسبة الخاصة بتغلب نسبة المبتكر على أوردرات البراند من التاريخ ده» and the plan's Review Focus 2 says the special rate *in force* wins. For maker rates the "earliest row before its date" fallback exists because a maker must always have some rate; for a *special* rate the natural value before the first row is "none" (→ the owner's rate), exactly what a `null` row means after it.
- Which test proves it: none proves the plan's intent for a date before the first row. The current behaviour is asserted by `tests/adapter/vendors.test.mjs` ('brands: the shape …': `S.rateFor(V2, '2026-09-30')` → `30` with `since: '2026-10-01'`) and `tests/domain/vendors-domain.test.mjs` (`effectiveRate(rows, '2026-09-01')` → `30`). The e2e special-rate test dates the row 15 days ago and the order 10 days ago, so it never crosses the boundary. Task B report, point 6, records this as a deliberate choice; I disagree with it for money reasons.
- Minimal fix: in `brandRateAt` start with `let r = null` (and in `effectiveRate` likewise), i.e. no special rate until a row has started; flip the two assertions above to `null` / `45` (the owner's rate). `rateFor` already falls back to the owner's `rateAt` when `brandRateAt` is null. Nothing in SQL changes (`brand_rates` has no server-side lookup).

**I2 — A transfer dated the same day as the last transfer gets the *rates* message («فيه نسبة متسجلة بنفس تاريخ السريان — اختار تاريخ تاني»).**
- `app/js/adapter/vendors.js:268` (`reasonOf`): `23505` → `'brand_exists'` only for `brands_name_key`, every other `23505` → `'duplicate'`, whose text (`MESSAGES.duplicate`, line 66) is about a rate; block 28 shows `VMSG[reason]` as-is (`28-app.js:1475`). `validateTransfer` deliberately lets `since === lastSince` through ("the same day: the server's unique key judges"), so this is the normal path, not an edge: the plan's own correction recipe (decision 1: «نقل غلط بيتصلح بنقل تاني … التاريخ المتكرر مرفوض — بنعمل نقل بتاريخ بعده») sends the user straight into it.
- Failing scenario: Antikiano's brand was moved to Bian eg from 18 Oct by mistake; the team opens «نقل لمبتكر تاني», picks Art Craft, keeps 18 Oct → the popup accepts, the server answers `23505 brand_owners_brand_id_since_key`, the local history is put back and the page says a *rate* exists with that date.
- Which test proves it: `tests/adapter/vendors.test.mjs` ('transferBrand …') asserts the reason `['duplicate']` for exactly this `23505`; no test asserts the text the page shows.
- Minimal fix: map `23505` whose message names `brand_owners_brand_id_since_key` to a new `MESSAGES.brand_same_date` («فيه نقل متسجل بنفس التاريخ — اختار تاريخ بعده»), or refuse `since === lastSince` locally in `validateTransfer` / `moveBrand` with that text (then the server's `23505` is only the race case). Update the one assertion.

**I3 — The maker report, the period statement and the share texts still attribute by store name; after a transfer they contradict the drawer's own KPIs.**
- `app/js/blocks/28-app.js:61-64` (`openVendorReport`: rows from `VD.vendorReport(orders, [v.name, ...v.aliases], st.balance)` — the balance comes from `stats()` (attribution-aware), the rows from `06-vendors-domain.js:234` `keys.includes(norm(s.vendor))`), `:404` / `:408` (`periodStatement`), `:421` (`weeklyVendorReport`), `:444` (`dailyVendorReport`), and the `vendor.share` flow at `:1807`.
- Failing scenario: with the seeded transfer (Antikiano → Bian eg from 8 days ago), Bian eg's drawer says 1 order / 1,513.40 pending; «تقرير المبتكر» for Bian eg lists none of Antikiano's store orders while Antikiano's report lists 181668 (which the drawer says is not his). The same text is what «مشاركة» sends to the maker.
- Which test proves it: none (no report / statement / share test after a transfer). Task B report, concern 1, records it and the plan's Later list defers the reports to SQL (`store_owner_at`) in phase 4.
- Minimal fix (if the owner wants it in this phase): build the report rows from `vendorStats()[v.id].orders` (already attributed) instead of a names list, or give `VD.vendorReport` / `periodStatement` / the weekly / daily reports a `(sub, order) => boolean` predicate that block 28 fills with `vstore.storeOwnerAt(sub.vendorId, order.date) === v.id`. Otherwise: say so in the drawer's report popup («التقرير بأسماء المتاجر لحد تقارير الحسابات») so a shared report is not wrong silently.

### Minor

- **M1** `28-app.js` `brandTransferForm` / `brandReturnForm` validate against `b.owner` (the owner *today*) while the adapter's `moveBrand` validates against the latest history row (`lastRow`, which may be future-dated — the same row the server's guard uses). With a future-dated transfer on file the popup passes and the store throws «البراند أصلًا عند المبتكر ده» for the wrong maker; the ⋮ menu's «رجوع لصاحبه» also keys off `owner !== origin`. No data harm. Fix: use the latest row's vendor in the popup (`vstore.brand(id)` could expose `lastOwner`).
- **M2** `brandByName` / the popup's duplicate check normalise with `norm` (`[\s_.-]` → space, Arabic digits), stricter than the server's `lower(btrim(name))`: «Wood-Rope» is refused locally while «Wood Rope» exists, although the server would accept it. Acceptable (prevents look-alikes), but the message says «بنفس الاسم».
- **M3** `vendor.brand.rate` writes the rate value into `activity_log.new_value`, and `toEvent` renders it in «سجل النشاط», which every member who can open the drawer reads (ops included) — the special rate leaks to roles without `sensitive.commission` through the log text. Same pattern as the existing `vendor.rate` (the plan explicitly keeps it), so recorded only; a fix would log «خاصة» without the number or filter `vendor.*rate` rows by `canRate()` in `fetchEvents`.
- **M4** `brand_owners_guard` reads the last row without a lock: two members transferring the same brand at the same moment with different dates both pass (the unique key only catches an equal date). Harmless for a 56-maker registry; `select … for update` on the brand's rows (or `pg_advisory_xact_lock(hashtext(new.brand_id::text))`) closes it.
- **M5** `addBrand` with the owner insert refused (`missing: ['owner']`) leaves a brand with no history; a later transfer then makes the *receiver* the first row and the origin never appears in the history (`brandsEver` empty for him, `brand_owner_at` before the date = the receiver). Edge of an edge; the page already warns «ناقص: صف الملكية».
- **M6** Deleting the origin maker cascades a brand that another maker holds today (0013 as decided; Task A concern 3) and the admin's `remove` has no confirmation naming it. Practically unreachable on the live registry (every maker has lines) — a line in the future settings-page delete confirm would do.
- **M7** `rls_brands.sql` has three counts scoped by *name* rather than by this file's ids (`count(*) … where name = 'ورشة النقل' and woo_vendor_id is null`, `… name in ('Test Popup Maker', 'ورشة النقل')`, lines 538 / 787) and two global "no orphan" counts (771–772, guaranteed by the FKs). A live hand-added maker named «ورشة النقل» would make the file *fail*, never touch a row. Live-safe as claimed.
- **M8** `writeBrand` announces a refusal with `emit({ id: ids[0], reason })` only; a transfer refused while the *receiver's* drawer is open shows no note there (the local history is put back in both drawers). In the shipped flows the user is always in `ids[0]`'s drawer.
- **M9** The mock refuses a `returning` select other than `id` and any `on_conflict` (stricter than PostgREST, which would serve them); not a kindness, fine — noted so nobody "fixes" the mock to be lenient.
- **M10** Deviations from the plan's letter, all justified and recorded: buttons gated by `canBrands()` (admin or `vendors.edit = F`, the server's policy) instead of `canEdit()`; no update policy / grant on `brand_owners`; the owner-row `set_by = 'system'`; `brand_owners.vendor_id` deferrable + the `vendors_brands_guard_delete` trigger (needed — I reproduced the reasoning: a NO ACTION key is checked before the second-level cascade removes the maker's own owner rows).
