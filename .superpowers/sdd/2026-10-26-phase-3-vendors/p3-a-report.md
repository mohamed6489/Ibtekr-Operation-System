## Under-specified in the plan — the choice made (please confirm or overrule)
1. **`vendors_update` with check admits `sensitive.vendor_bank = F`** (`is_admin() or vendors.edit <> 'N' or sensitive.vendor_bank = 'F'`), not the plan's literal `is_admin() or vendors.edit <> 'N'`. Why: decision 7 gives the contract to admin **and accounts**, but accounts has `vendors.edit = N` and would have been shut out of `update vendors set contract = …` by the literal with check; the guard then allows accounts the `contract` column alone (the test proves name / phone / notes / status are refused). Task B's mock emulates the guard per decision 8 (contract ← bank F), so this keeps server and mock consistent. Cost if wrong: none for other columns.
2. **`vendor_rates` and `vendor_bank` reference `vendors(id) on delete cascade`.** Why: the sensitive rows mean nothing without the maker, and otherwise an admin could never delete a hand-added maker (no orders) after setting a rate or a bank row; 23503 stays reserved for lines / sub-orders / products, which is what the brief lists and what B's mock emulates. The cascade is an integrity action (bypasses RLS by design) and only the admin's delete reaches it.
3. **`commission_pct` = the rate effective on `current_date`, refreshed on insert only**; a maker whose only rates are future-dated has `null` until the next insert. The screen reads `vendor_rates` itself (decision 3), so the copy is informational (service_role only). Documented in the migration.
4. **Backfill guards**: `joined_at` is cast from `left(registered, 10)` only when the value starts with `YYYY-MM-DD` (else `created_at::date`); the commission columns are cast only for a plain non-negative decimal (`^\d{1,3}(\.\d+)?$` / `^\d{1,8}(\.\d+)?$`), a non-array `meta_data` is skipped — nothing malformed can stop the file. The live pre-check in §2.1 counts the rows that would fall back.
5. **service_role grants** are written as `select, insert, update, delete` (what every other migration does) rather than a literal `grant all` followed by the revoke — the net privileges are identical.
6. **`joined_at` in the sync** is validated as a real calendar date (`2025-02-30` → null, like a malformed string) and never shifted by a zone (`registered` is a local datetime; the date Dokan shows is the date we store).
7. **`saveVendors` lookup**: ids already in `ctx.vendors` are not re-queried; the rest go through one `selectIn`. On the webhook path (`resolveVendors` → unknown stores) this is one extra, empty-result query per delivery that has an unknown maker — accepted for one code path.
8. **The positive admin delete is not exercised in SQL** (the brief forbids delete statements in tests; the expected-to-fail deletes run as `execute` strings like `rls_orders.sql`). «Admin only» is proven by the admin reaching the row (23503 from the lines) and non-admins touching zero rows; the cascade is asserted on `pg_constraint`. The e2e mock covers the positive path.
9. **`rls_vendors` asserts the trigger functions are owned by `postgres`** (true on the live project and in CI; a local run under another superuser would fail that one line).
10. **`vendors.updated_at` is never bumped by a member write** (no trigger in 0007 or 0011; the column is not in the update grant). If Task B's `lastUpdate` is meant to move on edits it must come from `activity_log` or a trigger in a later migration — flagging it rather than adding scope.
11. The guard's first rule («sync / server columns») can only be reached by a role that holds the column privilege; today the column grants refuse `woo_vendor_id` / `commission_pct` / `raw` / `opening_balance` / `updated_at` first (Postgres says «permission denied for table vendors», without naming the column). Both layers give 42501, as the brief asks.

- `create or replace trigger` needs Postgres 14+ (live 17, CI 17; a local 13 would fail).
- On the live project, `create policy … on storage.objects` must be allowed for the migration runner (`postgres`); this is the documented Supabase way to add storage policies, but it is the one statement I could not mirror locally (the block is skipped without a storage schema, and `rls_vendors` checks the bucket only when the schema exists).
- `revoke select, insert, update, delete on public.vendors from authenticated` comes before the column grants; PostgREST reloads its schema cache on DDL on Supabase, so members' `select=*` on vendors starts failing the moment 0011 is applied — Task B's adapter must already name its columns when the phase lands on `main` (the plan's order has 0011 first; the current `main` front end reads vendors only through `IBDirectory` — worth a check that it never selects `*` on `vendors`).
- Decision 2's cost holds: a store Dokan disables stays «active» here until the team toggles it (the sync rewrites raw only).
- The commission pair is sync-owned and rewritten on every run; a change of the site's commission on an old order would therefore propagate to that order's line on its next sync, which is what decision 4 («the rate when the order was placed, as the site has it») implies.
- For Task B / the mock: `insert … select=id` on vendors works (column grant on `id`), `returning *` does not; accounts may PATCH `contract` (server allows it); the server's 42501 messages are the English rule texts in the guard, or Postgres's «permission denied for table …» for a column grant, or «new row violates row-level security policy» for a policy — the screen should key on the code, not the text.
