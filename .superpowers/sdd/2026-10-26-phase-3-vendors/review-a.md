### Important
1. **`supabase/tests/rls_vendors.sql:490` — wrong expectation, the live run stops here.** Line 9402 is seeded with rate 40 / fee 10 (:65), so `1000 − (1000×40/100 + 10)` = **590**, not 640 (640 is the plan's 35 %/10 example). Role: ops. Fix (smallest): `9402=40.00/10.00→640.00` → `9402=40.00/10.00→590.00`. (b26c190 only added the "got %" diagnostics; the expectation is still 640 on HEAD.)
2. **`supabase/tests/rls_vendors.sql` ops refusal loop, entry `update public.vendors set category = 'هدايا' where woo_vendor_id = 441` (≈:503) — a no-op, so the guard lets it through and the case raises "expected 42501 … got P0001".** The admin already set `category = 'هدايا'` on 441 at :313; `new.category is not distinct from old.category` → no rule fires (by design, same as the orders guards). Fix: use a value that changes, e.g. `''أطعمة وحلويات''` (or target 442). With 1 + 2 fixed the whole file passes locally.
3. **`supabase/migrations/0011_vendors.sql:286–306` — the only part never executed anywhere: the Storage DO block on the live project.** `insert into storage.buckets` and `create policy … on storage.objects` run as `postgres`, which is not the owner of `storage.objects`; Supabase allows this (supautils policy grants / documented SQL-editor way), but verify on apply. If `apply_migration` errors with "must be owner of table objects", nothing before it is lost (idempotent file): apply the file without the block, then create the bucket + 3 policies from the dashboard/SQL, and `rls_vendors` will still assert them.
4. **`vendors.updated_at` is never bumped** — not by members (no touch trigger in 0007/0011, column not in the update grant: `update … set updated_at = now()` is 42501 — tested) nor by the sync's raw-only upsert. If Task B maps `lastUpdate` from `updated_at`, the screen shows the first-sync date forever. Yes, the guard can set it safely: a BEFORE trigger may assign any NEW column regardless of the caller's column privileges (privilege checks cover the statement's SET list only). Smallest fix in `vendors_guard_update`: after the `end if;` of the `current_user` block and before `return new;`, add `new.updated_at := now();` (outside the block so the sync's raw-only write bumps it too; after the comparisons so rule 1 keeps seeing the old value). Zero grant changes; `rls_vendors` needs one assertion. Decide now — 0011 is not applied yet.
