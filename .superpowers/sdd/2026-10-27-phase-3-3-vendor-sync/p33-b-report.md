## Under-specified points and my choice
1. **A member who may edit the contact (vendors.edit = P) but may not push (push_vendor needs F):** the adapter makes no request (the server would answer 401) and the page says «اتحفظ في السيستم بس — إرسال التعديل للموقع محتاج صلاحية تعديل المبتكرين الكاملة». Consequence (see concerns): his change is not in `push_pending`, so the sync never carries it to the site.
2. **`instagram` = `social.instagram`:** the old `@name` text field left the contact popup; the adapter writes `instagram` from the links with every social change (decision 1). The identity / contact rows of a maker without links show «—».
3. **A link that is not https:// coming from a row** (never, after Task A's blanking) is blanked by the adapter too (`cleanSocial`), so the drawer shows nothing and the popup an empty field; html inside an https link is a link whose text is the label and whose href is the literal value (inert, tested).
4. **The address row** shows `addressText(parts)` when any part is filled, else the typed `address` text (a maker from before 3.3). Zip / country go on their own row «الرمز البريدي / الدولة».
5. **`categoryRates`** carries the row in force today per category with a rate; a null row (removed) drops the category from the list; the add popup lists the categories without a current rate, «تعديل» on a row keeps the category fixed. A category rate dated the same day as an existing row is refused locally (`category_duplicate`) before the server's 23505.
6. **The flat fee** rides on the rate row only when given (`flat` absent from the insert otherwise, so the phase-3 assertions stay); a changed flat with the same rate counts as a rate change (a new dated row). It is display only, as decided.
7. **`push_vendor` for a maker without a store** is skipped locally without a request (`no_store`) — the server's answer is the same.
8. **The sync rows' attribution** (security review): `vendor.sync*` rows read as «الموقع» only with `actor` null; with an actor they read as that member's generic event.
9. **The seeded sync rows** are opt-in (`{ syncRows: true }`): seeded by default they entered the dashboard's «newest 5 server rows» case.
