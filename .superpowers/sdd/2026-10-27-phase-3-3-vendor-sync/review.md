## Findings

### Important

**I-1. A push that never reached the function is not marked `push_pending`, so the sync never carries it — while the page promises «هيتبعت مع المزامنة الجاية».**
- `app/js/adapter/vendors.js:357` (`!cl || !uid()` → `error/network`), `:360` (`functions.invoke` error → `forbidden` / `failed` / `woo_error`), `:365` (thrown → `network`): only the 502 path (`woo-sync/index.ts:235`) and `push_disabled` (`:221`) mark the row pending server-side. A browser-side network failure, a cold-start timeout, an expired session (401), a 500 before `markPushPending`, or a gateway error leave `push_pending` untouched.
- `supabase/functions/_shared/woo-write.js:285` — the sync pushes `pending.filter(f => diff[f] === 'system')` only; a non-pending `system` field is left alone forever (Task A point 1, deliberately, to avoid re-pushing what Dokan refused).
- `app/js/blocks/28-app.js:1483` shows `VMSG.push_failed` («… هيتبعت مع المزامنة الجاية») for every `result: 'error'`, which is true for 502 only.
- Failing scenario: the admin edits Art Craft's phone; the Edge Function is cold / the user's JWT just expired; the row is saved here, the toast says it will go with the next sync; the next sync sees `phone: 'system'`, not pending → the site keeps the old phone indefinitely, no log row says so. (The adapter test `pushVendor answers (3.3)` asserts the `network` answer but nothing asserts pending-ness for it; no test covers this path end-to-end because nothing can.)
- Minimal fix (SQL + adapter): a `security definer` RPC `vendor_push_pending(p_vendor uuid, p_fields text[])` (admin or `vendors.edit` F, or P for the contact fields — the same rule as `push_vendor`; fields ⊆ SYNC_FIELDS; `push_pending := push_pending ∪ p_fields`), called by the adapter on every `result: 'error'` except `woo_error` (already pending); if that call fails too, change the toast to «… حاول تاني من «تعديل»» instead of promising the sync. Alternative without SQL: the adapter re-invokes `push_vendor` for the failed fields on the next `load()` (sessionStorage), and the toast says so.

**I-2. A rate dated in the future — or dated "today" in Cairo while the UTC date is still yesterday — is pushed as the *currently effective* rate and then never pushed again when its date arrives.**
- `supabase/functions/woo-sync/index.ts:229` → `effectiveRates(ctx, [vendorId], run.now())` → `woo-write.js:181` `today = dateOf(now)` (UTC): the PUT carries the latest row with `since <= UTC today` — the Deno test `push_vendor: the commission fields …` even asserts "not the future 50". Then `applyPushResult` writes the *site's answer* (the old rate) into the snapshot.
- When the date arrives: `diffStore` → `rate: 'system'`, not pending → never pushed (`woo-write.js:285`). Worse: marking it pending would not help today, because `woo-write.js:314` drops a pending field whose verdict is `same` at the next run (the new row is not effective yet, so site == ours == snapshot).
- The UI allows it: `app/js/blocks/10-ui-kit.js:195` `DateField` has no max; `28-app.js:1722` (`g-since`) / `:1985` (`cr-since`) accept any date; the adapter's `today()` is the browser's local date (`vendors.js:122`) while the server's is UTC — between 00:00 and 02:00 Cairo time (03:00 under DST) a rate dated "today" is a future rate for the server.
- Failing scenario: on 2026-11-01 the admin sets Art Craft to 40 % «سارية من 2026-12-01» (the popup says «والنسبة بتتبعت للموقع»). The push sends 35 % (today's), `accepted`. On 1 December our share arithmetic uses 40 %, Dokan keeps charging 35 %, nothing is pending, nothing is logged. Same for `setCategoryRate`. No test covers the day the future row takes effect.
- Minimal fix: (a) in `pushVendor` (index.ts), when the maker's newest `vendor_rates` / `vendor_category_rates` row has `since > today`, mark `rate` / `category_rates` pending and answer `skipped/future` (the page can say «هتتبعت يوم …»); (b) in `syncVendor`, keep a pending `rate` / `category_rates` whose verdict is `same` (do not clear on `same` for the two rate fields), so the run on the effective day sees `system` and pushes; (c) compute the server's "today" in `Africa/Cairo` (one `Intl.DateTimeFormat` call) or pass the adapter's local date in the body for `since` comparison only. The cheapest stop-gap is (d): the popup refuses `since > today` for a maker with a store.

**I-3. A field Dokan refuses with a 4xx is retried every 15 minutes forever, one failing PUT and one `woo_sync_log` error row per run per store (review focus 8).**
- `woo-write.js:305-310`: a `WooError` keeps the fields pending (`settled = []`), with no counter, backoff or distinction between a transient 5xx / network error and a deterministic 4xx (`rest_invalid_param`, `dokan_rest_cannot_edit`). `index.ts:235` does the same for the adapter's push.
- Failing scenario: ops saves an e-mail Dokan's `sanitize_email` rejects, or the WP application password is revoked (401): from then on every cron run makes a PUT that fails and writes an error row — 96 rows a day per stuck store, 55 stores if the credentials are the cause. The Deno test `store sync — pending push …` asserts exactly that the 400 keeps the field pending; nothing bounds it.
- Minimal fix: in the sync's catch, when `e.status` is a 4xx other than 401 / 403 / 408 / 429, drop those fields from `push_pending` and log one `out/vendor` row `result: 'refused'` (+ an activity row `vendor.sync.refused` so the drawer shows it); keep 5xx / network / 401 / 403 retrying. Optionally a `push_attempts` counter in `push_pending` (object instead of array) capped at, say, 8.

### Minor

**M-1. `vendor_rates` is "add-only" for members but the sync upserts on `(vendor_id, since)` and overwrites a member's row of the same day** (`woo-write.js:209-213`, `set_by` becomes «الموقع», the member's figure is gone). Task A's concern. Fix: `on conflict do nothing` + a conflict log row when today's row exists and differs (the next day's run writes the site's row), or keep the upsert but copy the replaced row into `woo_sync_log.detail` (figures only, no PII).

**M-2. Status permission mismatch between the guard and the push.** `0014` guard: `status` ← `vendors.toggle = F`; `push_vendor` / `canPush`: `status` needs `vendors.edit = F` (`index.ts:90-91`, `vendors.js:259`). A member with `toggle F` + `edit P` saves «موقوف» here, gets `no_permission`, nothing pending → the store stays enabled on the site. None of the five built-in roles of 0003 has that combination, so it is latent. Fix: admit `vendors.toggle = F` for a `status`-only push in `authorize` and `canPush`.

**M-3. `toDokanCommission` with category rates but no base rate sends `all.percentage: ''`** (`woo-core.js:384-394`): a `category_based` block whose default is empty — Dokan may store 0 % for every uncovered category. Reachable when `setCategoryRate` is used on a maker without a `vendor_rates` row (the popup does not require one). Fix: refuse `category_rates` without an effective rate (`toDokanCommission` → null → `dropped`, and the popup says so).

**M-4. Every run rewrites every store row** (`woo-write.js:286` `woo_synced_at: now` + the guard's `new.updated_at := now()` at `0014:186`): 55 UPDATEs per 15 minutes and `vendors.updated_at` churn. Pre-existing (phase 3 wrote `raw` each run) and `lastUpdate` is not shown in block 28, so cosmetic; writing `woo_synced_at` / the snapshot only when something differs would make the run almost free.

**M-5. UTC vs Cairo dates.** A site-side rate change arrives as a `vendor_rates` row `since = UTC date` (`woo-write.js:209`), while the adapter's rows carry the Cairo date — a site change at 01:00 Cairo is dated "yesterday" here. Harmless for the share (the line's own commission wins), confusing in «سجل النسبة». Same root as I-2 (c).

**M-6. Pushing `email` changes the vendor's WordPress login e-mail** (Dokan's `update_store` writes `user_email`). Decision 1 covers it, but the acceptance check (§2.7.11) should record it explicitly and the owner should know a typo by ops locks the maker out of his account / moves his notifications. Not a code defect.

**M-7. After the first run, every `conflict` field (the six placeholder names, any differing phone / e-mail / rate) stays a permanent silent `system` difference** — ours stays, nothing is pushed, `commission_pct` keeps ours while the site charges its own. By design (Task A point 1, owner's answer 2), but §2.7.11 only pushes store 2376: the run's `conflict` rows need a one-time pass (re-save the field here, or `push_vendor` with the listed fields) and the deploy doc should say so.

**M-8. Sync activity rows are visible to `settings.view` only** (0006 policy, the ledger's ruling): accounts / cs never see «اتعدل من الموقع» in the drawer. Noted, not a defect of this phase.

**M-9. Pre-existing: `Access-Control-Allow-Origin: *` on woo-sync** (`index.ts:65`) with Bearer auth — fine for a JWT-authenticated function, noted for the security sheet.
